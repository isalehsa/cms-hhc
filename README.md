# نظام إدارة الالتزام — Compliance Management System (CMS)

منصة موحدة لإدارة الالتزام المؤسسي متوافقة مع **ISO 37301**، مصممة لإدارة الالتزام في شركة صحية قابضة. تعمل بالكامل على **الخطة المجانية (Spark) من Firebase** — بلا خادم إطلاقاً: الاستضافة على Firebase Hosting، والبيانات دائمة في Cloud Firestore، والمصادقة عبر Firebase Authentication، وكل المعالجة تجري داخل متصفح المستخدم.

## الوحدات

| الوحدة | الوظيفة |
|---|---|
| 🏠 **لوحة التحكم** | مؤشر نسبة الالتزام، خرائط حرارية 5×5 للمخاطر (كامنة/متبقية)، الغرامات المتوقعة والمتجنَّبة بالريال، تقويم التزام شهري، توزيع الضوابط، التنبيهات |
| 📖 **مكتبة الالتزام** | تبويبان: **موسوعة الوثائق** (إضافة الوثائق وتحليلها عبر نافذة، آخر تحديث، عدد البنود) و**المكتبة المفصلة** (المتطلبات بنداً بنداً انعكاساً لمواد الوثائق، بالإدارة المالكة والأهمية والغرامة، مربوطة بالمخاطر) |
| ⚠️ **سجل المخاطر** | تقييم 5×5 قبل الضوابط وبعدها، خريطة حرارية تفاعلية، تقدير الغرامات مالياً، ضوابط مصنفة (وقائي/كشفي/تصحيحي/توجيهي)، خطط المعالجة، مؤشرات KRI |
| 🛰 **الرصد التنظيمي** | رصد المستجدات التنظيمية من مصادرها الرسمية (فحص أسبوعي مجدول + تشغيل يدوي)، وتحليل انطباقها وأثرها بالذكاء الاصطناعي، ومراجعة الالتزام لها، ثم اعتمادها لتتولّد منها آلياً: التزامات في مكتبة الالتزام، ومخاطر بضوابطها، وأنشطة مراقبة، ومبادرات خطة، وفجوات وخطط تصحيح، وفحوصات ذاتية — مع مواعيد تنظيمية وتقارير أسبوعية |
| 🔍 **برنامج المراقبة** | أنشطة رقابية مبنية على المخاطر، النتائج تولّد ملاحظات تلقائياً |
| 📅 **الخطة السنوية** | تبويبات حسب المحاور الستة (المتابعة، التحقق، الإرشاد، الرقابة، التدريب والتوعية، التطوير المستمر)، أنواع مبادرات شاملة، توليد تلقائي |
| 🎓 **التدريب والتوعية** | برامج التدريب وحملات التوعية، الجمهور المستهدف، أعداد المتدربين ونسب الإنجاز، الربط بالمتطلبات |
| 📊 **تقييم نضج التجمعات** | تقييم نضج الالتزام (ISO 37301) بـ7 محاور و40 معياراً (0-3): تقييم ذاتي للتجمع، ومراجعة ربعية وإعادة تقييم بالأدلة من مدير الالتزام، ونتائج ربعية بمصفوفة المحاور. استيراد/تصدير نموذج التقييم بصيغة Excel، وخانة رابط واحد لمجلد الأدلة مع إرسال بريد إلكتروني بالرابط، ورفع ملف دليل داعم لكل بند على حدة |
| 📇 **دليل التواصل** | جهات اتصال قيادات التجمعات: إضافة/تعديل/حذف، استيراد وتصدير Excel، مراسلة واتساب فردية وجماعية وبريد، وخانة البريد الرسمي للإدارة |
| 📋 **الفحص الذاتي** | نماذج للإدارات مرتبطة بالمتطلبات، عدم الالتزام يولّد ملاحظات |
| 🛠 **الملاحظات والتصحيح** | خطط تصحيحية بمسؤولين وتواريخ وتقدم، واعتماد الإغلاق |
| 📨 **سجل المراسلات** | الخطابات الواردة والصادرة مع الجهات، استحقاق الرد والتنبيه على التأخر، ربط بالمتطلبات |
| 🗂 **سجل الإفصاحات** | تعارض المصالح، الهدايا والضيافة، الإفصاحات المالية، البلاغات — مع المراجعة والاعتماد والمعالجة |
| 🤖 **التحليل الذكي** | رفع نص/PDF/Word لاستخراج المواد وتصنيفها آلياً (Claude API + OCR) مع استخراج الغرامات والعقوبات |
| 📊 **التقارير** | 7 تقارير قابلة للتصدير Excel / PDF / Word بملخص تنفيذي ومؤشرات |
| ⚙️ **الإدارة** | المستخدمون والأدوار الستة + سجل تدقيق غير قابل للعبث |

**الترابط التلقائي:** المتطلب ← مخاطر ← أنشطة مراقبة ← ملاحظات ← خطط تصحيح ← الخطة السنوية — وكل وثيقة تعرض روابطها، والتقارير تسحب من جميع الوحدات.

**التحديث الآلي لسجل المخاطر:** بعد اكتمال تحليل أي نظام بالذكاء الاصطناعي يُضاف النظام آلياً كمتطلب في مكتبة الالتزام، وتُشتق منه مخاطر مرتبطة وفق الغرامات والعقوبات والمخالفات المذكورة في مواده (شدة الأثر تُقدَّر من نوع العقوبة: سجن/إلغاء ترخيص = 5، غرامة مالية/إيقاف = 4، جزاءات أخرى = 3). كما يفحص المحرك عند تسجيل الدخول — وبزر «⟳ تحديث آلي» في سجل المخاطر — الإضافات الحديثة في المكتبة وينشئ خطر عدم التزام لكل متطلب بلا مخاطر. المحرك آمن التكرار ولا ينشئ سجلات مكررة.

**الأدوار:** مدير النظام، مدير الالتزام، أخصائي الالتزام، مالك الإدارة (يجيب على فحص إدارته ويحدّث تقدم إجراءاتها فقط)، مسؤول التزام تجمع صحي (يرى فقط أداة التقييم الذاتي ونتائج التقييم الربعي لتجمعه)، مراجع، الإدارة التنفيذية — تفرضها قواعد أمان Firestore على مستوى قاعدة البيانات.

## النشر خطوة بخطوة (مرة واحدة)

### 1) إنشاء مشروع Firebase

1. ادخل إلى [console.firebase.google.com](https://console.firebase.google.com) وأنشئ مشروعاً جديداً (الخطة المجانية Spark تكفي).
2. من **Build → Authentication → Get started** فعّل طريقة الدخول **Email/Password**.
3. من **Build → Firestore Database → Create database** أنشئ قاعدة البيانات (وضع Production — القواعد تُرفع من هذا المستودع).
4. من **Project settings (⚙) → Your apps → أيقونة الويب `</>`** سجّل تطبيق ويب جديداً وانسخ كائن `firebaseConfig`.

### 2) ضبط ملفات المشروع

- الصق قيم `firebaseConfig` في الملف **`public/js/firebase-config.js`** (هذه القيم عامة وغير سرية — الحماية الفعلية عبر قواعد أمان Firestore).
- ضع معرّف مشروعك في **`.firebaserc`** بدل `YOUR_FIREBASE_PROJECT_ID`.

### 3) إنشاء المستخدمين وأدوارهم

1. من **Authentication → Users → Add user** أنشئ حساب مدير الالتزام (بريد + كلمة مرور)، وحسابات الاستعراض إن أردت.
2. انسخ **UID** الخاص بكل مستخدم من نفس الشاشة.
3. من **Firestore Database → Start collection** أنشئ مجموعة باسم `users`، وأضف وثيقة لكل مستخدم:
   - **معرّف الوثيقة (Document ID)** = UID المستخدم.
   - الحقول:

     | الحقل | النوع | القيمة |
     |---|---|---|
     | `role` | string | `compliance_manager` لمدير الالتزام أو `viewer` للاستعراض |
     | `display_name` | string | الاسم الظاهر في الواجهة (مثل: مدير الالتزام) |

   أي مستخدم بلا وثيقة دور يُعامل تلقائياً كمستعرض (قراءة فقط).

### 4) النشر

```bash
npm install -g firebase-tools
firebase login
firebase deploy
```

سينشر الأمر الاستضافة **وقواعد أمان Firestore وقواعد التخزين (Storage)** معاً، ويعطيك الرابط العام بصيغة:
`https://YOUR_PROJECT_ID.web.app`

عند أي تعديل لاحق يكفي `firebase deploy` مرة أخرى — **البيانات في Firestore لا تتأثر بإعادة النشر**.

> **تفعيل التخزين (Storage):** ميزة رفع ملفات الأدلة الداعمة في تقييم نضج التجمعات تعتمد Firebase Storage. فعّله لمرة واحدة من **Firebase Console ← Build ← Storage ← Get started**، ثم انشر قواعده بأمر `firebase deploy` (القواعد في `storage.rules`). دون تفعيله يظل بقية النظام يعمل، ويظهر تنبيه واضح عند محاولة الرفع.

## التحليل الذكي (Claude API)

- يُدخل مدير الالتزام مفتاح Claude API من زر **⚙** أعلى الصفحة. المفتاح **يُحفظ في متصفحه فقط** (localStorage) ولا يُرسل لأي جهة غير Anthropic، ولا يراه بقية المستخدمين.
- **مع المفتاح**: تُحلَّل النصوص بنموذج Claude مباشرة من المتصفح (مخرجات مقيدة بمخطط JSON صارم) فيُستخرج كل بند مع تصنيفه ومبرره.
- **بدون مفتاح**: يعمل محلّل نصي احتياطي يقسّم النص إلى مواد (المادة/البند/الفصل...) بقيم افتراضية، وتُعلَّم جميع البنود «بحاجة لمراجعة» ليصنّفها مدير الالتزام يدوياً.
- التحليل يجري داخل صفحة المتصفح — لا تغلق الصفحة قبل اكتماله (تظهر حالة التقدم في الواجهة).

## 🛰 الرصد التنظيمي وإدارة التغيير (Regulatory Intelligence)

وحدة داخل النظام — لا تطبيق منفصل — تصل ما يصدر عن الجهات الرقابية بوحدات الالتزام القائمة.

### المسار الكامل

```
مصدر رصد → فحص (أسبوعي مجدول أو يدوي) → مستجد تنظيمي → تحليل ذكي (انطباق/أثر/التزامات/مخاطر/مواعيد)
   → مراجعة الالتزام → اعتماد → دمج آلي:
        سجل التغيّر التنظيمي · مكتبة الالتزام · سجل المخاطر والضوابط · برنامج المراقبة
        · الخطة السنوية · الفحص الذاتي · الملاحظات وخطط التصحيح والأدلة
```

كل سجل مولَّد يحمل `regUpdateId` فيمكن التنقّل في الاتجاهين: من المستجد إلى التزاماته ومخاطره وضوابطه
وأنشطة مراقبته وفجواته وإجراءاته وإداراته، ومن أي متطلب أو خطر إلى المستجد التنظيمي الذي أنشأه.

### التبويبات

لوحة الرصد · المستجدات التنظيمية · بانتظار المراجعة · مصادر الرصد · الالتزامات المولّدة ·
المواعيد التنظيمية · الإجراءات التنظيمية · التقارير الأسبوعية.

### المصادر والفحص

- تدعم المصادر: **RSS/Atom** و**واجهات JSON** و**استخراج روابط صفحات الويب** (بنمط تصفية اختياري) و**الإدخال اليدوي**.
- **الفحص الأسبوعي المجدول** (الأحد 05:00 بتوقيت الرياض) يعمل عبر مهمة **GitHub Actions** (`.github/workflows/regulatory-scan.yml`)
  تشغّل المحرك نفسه بـ `functions/scan-runner.js` — **بلا حاجة إلى خطة Blaze**. ويمكن تشغيله يدوياً من
  Actions ← Regulatory Scan ← Run workflow (بخيار `scan` أو `report` أو `both`).
- زر **⟳ تشغيل الفحص الآن** داخل التطبيق يستدعي `/api/regintel/scan` في دوال Firebase — يعمل فقط عند نشر الدوال (خطة Blaze).
- **قفل ذرّي** يمنع تشغيل فحصين كاملين في وقت واحد، ويُكسر تلقائياً بعد 30 دقيقة إن تعلّق.
- **منع التكرار** بمفتاح ثابت لكل عنصر (المعرّف الخارجي أو الرابط المطبَّع)، فلا تتضاعف المستجدات بين الفحوصات.
- قائمة **مصادر رسمية سعودية** جاهزة للبذر — تُضاف **معطّلة** ويفعّلها مدير الالتزام بعد التحقق من كل مصدر.

### التحليل بالذكاء الاصطناعي

- **في المتصفح**: بمفتاح Claude الخاص بمدير الالتزام (نفس مفتاح التحليل الذكي المحفوظ محلياً).
- **في الخادم**: بسر `ANTHROPIC_API_KEY` في Google Secret Manager — لا يصل المتصفح إطلاقاً.
- **بدون مفتاح**: يعمل تحليل نصي مبدئي (كلمات مفتاحية + أنماط العقوبات + استخراج المواعيد)،
  وتبقى كل النتائج موسومة بطريقة تحليلها وتمرّ على مراجعة بشرية قبل الاعتماد.
- المخرجات مقيّدة بمخطط JSON صارم: ملخّص تنفيذي، قرار الانطباق ومبرره، درجة الأثر، الالتزامات
  (بالإدارة المالكة والأهمية والاستحقاق والدليل المطلوب وتوقّع الفجوة)، المخاطر بضوابطها، المواعيد، الإجراءات الموصى بها.

### الإعداد

1. من **🛰 الرصد التنظيمي ← 🌐 مصادر الرصد** أضف المصادر (HTTPS فقط) أو ابذر القائمة الرسمية ثم فعّل ما تتحقق منه.
2. من **⚙ الإعدادات** اضبط سياق المنشأة والتحليل التلقائي والتقرير الأسبوعي.
3. لتفعيل التحليل الذكي في الخادم: أضف السر `ANTHROPIC_API_KEY` (راجع `functions/.env.example`).

### الأمان

| الحماية | التنفيذ |
|---|---|
| **SSRF** | HTTPS فقط، بلا بيانات دخول، منفذ 443 وحده، تحليل DNS ورفض كل النطاقات الداخلية (IPv4 وIPv6 والعناوين المُسقطة)، متابعة التحويلات يدوياً بإعادة الفحص لكل قفزة (3 كحد أقصى)، مهلة 15 ثانية، وسقف 2 م.ب للاستجابة |
| **حقن التعليمات** | محتوى المصادر يُعقَّم (إزالة المحارف الخفية ووسوم الأدوار وأسوار الشيفرة) ويُغلَّف بين حدّين ويُقدَّم للنموذج كبيانات لا كتعليمات، والمخرجات مقيّدة بمخطط، ولا يُكتب أي سجل في وحدات الالتزام قبل اعتماد بشري |
| **الصلاحيات** | القراءة لكل مسجَّل · إضافة المصادر والمستجدات وتحليلها للمحرر · **الاعتماد والدمج وتشغيل الفحص لمدير الالتزام وحده** — مفروضة في قواعد Firestore لا في الواجهة فقط |
| **الأسرار** | مفتاح الخادم في Secret Manager، ومفتاح المتصفح في جهاز المستخدم وحده — ولا مفتاح ثابت في الشيفرة |
| **سجل التدقيق** | كل رصد وتحليل واعتماد ودمج وسجل مولَّد له قيد في `auditLog` غير قابل للتعديل أو الحذف |

### حدود معروفة

- **الموصلات المتحقَّقة**: RSS/Atom و JSON و استخراج روابط HTML و الإدخال اليدوي — مُختبرة بتجهيزات ثابتة (fixtures).
  أما المصادر الرسمية المبذورة فمعطّلة افتراضياً لأن توفّر تغذية قابلة للقراءة الآلية يختلف من جهة لأخرى ويحتاج تحققاً يدوياً.
- **حالة مشروع `cms-hhc` اليوم: خطة Spark**، فتُنشر الاستضافة وقواعد Firestore بنجاح بينما يفشل نشر الدوال
  برسالة `must be on the Blaze (pay-as-you-go) plan`. ولهذا يعمل **الفحص الأسبوعي والتقرير عبر GitHub Actions**
  بدل الدوال المجدولة. الذي يبقى معطّلاً حتى الترقية إلى Blaze هو فقط: زر «⟳ تشغيل الفحص الآن» داخل التطبيق،
  ومسار REST‏ `/api/regintel/scan`، والملخّص البريدي اليومي وتصعيد مسارات الاعتماد (دوال سابقة لهذه الوحدة).
  وبعد الترقية يكفي إعادة تشغيل سير النشر — الشيفرة والجدولة وربط الأسرار جاهزة.
- **إعادة ربط DNS** (DNS rebinding): يُعاد تحليل الاسم داخل `fetch` بعد فحصنا، وإغلاق هذه النافذة كلياً يحتاج وكيل خروج مقيّداً بقائمة عناوين.
- التحليل النصي المبدئي لا يشتق التزامات — يصنّف الانطباق والأثر والمواعيد فقط ويترك الاشتقاق للمراجع أو للتحليل الذكي.

## الصلاحيات

| الدور | القيمة في وثيقة `users` | الصلاحية |
|---|---|---|
| مدير الالتزام | `compliance_manager` | إضافة وتعديل وحذف وربط وإعادة تحليل |
| مستعرض | `viewer` (أو بلا وثيقة) | استعراض وتصدير فقط |

القراءة تتطلب تسجيل الدخول — لا يوجد وصول عام للبيانات. القواعد كاملة في `firestore.rules`.

## ملاحظات وحدود

- **حصص الخطة المجانية لـ Firestore** (1 غيغابايت تخزين، 50 ألف قراءة و20 ألف كتابة يومياً) كافية جداً لهذا الاستخدام.
- **حد وثيقة Firestore هو 1 م.ب** — نص النظام الواحد يجب ألا يتجاوزه (لا يحدث عملياً؛ قسّم اللوائح الضخمة إن لزم).
- **OCR**: ملفات PDF بلا طبقة نصية تُعالج تلقائياً بالتعرف الضوئي داخل المتصفح. أول استخدام يُنزّل بيانات اللغة (~15 م.ب) في متصفح المستخدم، وتُخزَّن مؤقتاً بعدها. الحد الأقصى 40 صفحة لكل ملف، وننصح بمراجعة النص المستخرج لأن دقة OCR تعتمد على جودة المسح.
- **حجم الملفات**: حتى 25 م.ب للملف الواحد (PDF أو .docx — صيغة .doc القديمة غير مدعومة).
- نسخة الخادم السابقة (Express + Render) محفوظة في تاريخ Git إن احتجت الرجوع إليها.
